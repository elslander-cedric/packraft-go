# Manual scripts

These scripts are manual only: never part of `npm test`, `npm run e2e` or CI. They call free public services, so run them one at a time and never in a loop.

## Live BRouter check

`npm run check:brouter`. Calls the public BRouter server four times, one request at a time with a 2 s pause, identifying itself with the project URL only. It compares each answer with its recorded fixture in `src/routing/fixtures/` and with what the adapter makes of it, then prints MATCH / DRIFT / MISMATCH per check. Exit code 1 means a mismatch: the live app is probably broken. Drift alone passes and means "consider re-recording". Run it now and then (e.g. monthly), or when live routing misbehaves while the tests pass. Don't run it in a loop: it's a free community server. It never writes fixtures; re-recording stays a deliberate, manual step. Logic: `src/routing/liveCheck.ts` (unit-tested offline); entry point: `scripts/check-brouter.mts`.

## Live KiWIS check

`npm run check:kiwis` (#64). Makes two requests to the SPW hydrometry service (the series list, then the values of those series), one at a time with a 2 s pause, no retries, identifying itself with the project URL only. It compares the answers with the recorded fixtures in `src/hydrometry/fixtures/` and with what the KiWIS adapter makes of them: table layout, series names, value columns, and the time offset (timestamps must be Belgian local time with its offset, +01:00 / +02:00, because the 08:00 reading is picked from the text; UTC is a MISMATCH). Prints MATCH / DRIFT / MISMATCH; exit code 1 means a mismatch (live Walloon flows are probably broken). Drift alone passes. Never writes fixtures; re-record by hand only on a mismatch. Logic: `src/hydrometry/liveCheck.ts` (unit-tested offline); entry point: `scripts/check-kiwis.mts`.

## Live PKAYAK check

`npm run check:kayak` (#218, ADR 0035). The SPW's `PKAYAK` map service is undocumented, so this is how we notice when its fields or codes change. Makes four requests, the app's own queries, one at a time with a 2 s pause, no retries, identifying itself with the project URL only (the same `User-Agent` as `prepare:spw-data`; the service answered 403 to `packraft-go-kayak-check`): layers 5 and 0 as the page asks them, layers 3 and 1 as `prepare:spw-data` does. It compares the answers with the recorded fixtures in `src/kayak/fixtures/` and prints MATCH / DRIFT / MISMATCH.

- MISMATCH (exit code 1, the app is probably broken): a layer that doesn't answer, answers with an error (ArcGIS reports its errors inside a 200, as it does for a field that doesn't exist) or holds no records; a field the app asks for that's gone; a status code the app doesn't know (it reads as unknown, so that stretch loses its status); a stretch or incident the adapter drops.
- DRIFT (passes, look at it when you can): a field of another type or a new field; another number of stretches, aires or obstacles (incidents come and go, so theirs is never drift); a stretch that came or went; an obstacle code the app doesn't show, or anything else that would make `prepare:spw-data` refuse. These leave the shipped snapshots standing, but the next refresh needs a decision.

Never writes fixtures; re-record by hand only on a mismatch. Logic: `src/kayak/liveCheck.ts` (unit-tested offline); entry point: `scripts/check-kayak.mts`.

## Live base map check

`npm run check:basemaps` (#179, ADR 0031; overlays #180, ADR 0032). Asks every base map and overlay source for one tile: OpenTopoMap, the Walloon SPW orthophoto WMS, the Flemish orthophoto WMTS, Brussels' UrbIS, the NGI's CartoWeb.be topo, then Waymarked Trails' hiking overlay. One request at a time with a 1.5 s pause, no retries, identifying itself with the project URL only. Prints OK / FAILED per source (FAILED with the HTTP status, a non-image answer or the network error, and the URL asked for); exit code 1 means a source failed and that base map or overlay is probably broken in the live app. Run it now and then, or when a base map shows blank tiles. Logic: `src/map/baseMapCheck.ts` (unit-tested offline); entry point: `scripts/check-basemaps.mts`.

## SPW snapshots

`npm run prepare:spw-data` (#206, #214, ADR 0035). Makes three read-only GETs to the SPW's public `PKAYAK` map service, one at a time with a 2 s pause, no retries, identifying itself with the project URL only: layer 5 (each official stretch's id, name and line), layer 3 (the aires) and layer 1 (the obstacles). It writes `src/access/data/official-stretches.json` (ids and names only), `official-aires.json` and `obstacles.json` with the source and today's date, and the lines to `docs/research/data/spw-stretch-lines.json`, which isn't shipped: the Walloon stretch mapping is checked against it (#209). It writes nothing if anything fails a check: an unknown aire type (only `E`, `D`, `ED` and `NA` are known), an unknown obstacle code (only `2`, `8`, `15`, `21` and `22` are known; a new one is a deliberate decision), an aire on an unknown stretch, a missing name, date or position, a repeated id, or an answer cut off by the service's record limit. Refresh it now and then and review the diff before committing; the app never queries this data at runtime. Logic: `src/access/prepare/spw.ts` (unit-tested offline); entry point: `scripts/prepare-spw-data.mts`. To add a layer, add a build function there and a step in the script.

## Walloon stretch geometry

Walloon stretch geometry (#54, ADR 0024):
  1. `npm run data:walloon-stretches` builds the 28 stretches from `docs/research/data/walloon-stretches.json` (Annex 1/2), OSM and the review decisions. OSM comes from Overpass: one query per river plus one for the national border, one request at a time, project URL as User-Agent. Answers are cached in `.cache/osm/` (git-ignored), so re-runs don't re-fetch; delete that folder to refresh from OSM (`--offline` refuses to fetch). If Overpass is busy, re-run: cached answers are kept, or set `OVERPASS_URL` to another public instance. The script writes a draft to `.cache/walloon-stretches.draft.json`, and writes the shipped `src/data/walloon-stretches.json` only when no end point needs review (official split boundaries, below, excepted). `--shipped` uses no OSM at all: it takes the shipped lines as they are and only cuts them again at the official boundaries.
  2. `npm run review:walloon-stretches` serves the review page at http://localhost:3461 (`REVIEW_PORT` to change). It shows every stretch; orange end points need review. Confirm a point, or drag it and save the move; each choice is written at once to `docs/research/data/walloon-stretches-review.json` (commit it) and the stretches are rebuilt from the cache. A confirmed point that OSM later moves by more than 30 m needs review again. With no `.cache/osm/` the page works from the shipped lines: official boundaries work as usual, and moving any other end needs step 1 first.

  **Official stretches (#209, ADR 0035).** After the build, `src/dataprep/walloonStretches/official.ts` gives each record its official stretch and cuts a record that spans two, or an official stretch and a long unlisted part. The pieces are `1A4-1`, `1A4-2` (`splitOf` names the record) and keep its category, thresholds and gauge. A boundary ships as `needsReview` and is listed under `review.pending` in the dataset until it is confirmed or moved on the review page, which draws the SPW's lines dashed, one colour per official stretch, and lists where the mapping and the lines differ. To split another record, add it to `OFFICIAL_MAPPING` and run `npx tsx scripts/walloon-stretches/build.mts --shipped`. The lines are in `docs/research/data/spw-stretch-lines.json`, written by `npm run prepare:spw-data`; they aren't shipped in the app, and the data tests check the mapping against them.
  3. Re-run step 1 to write the shipped dataset.
  End-point recipes (which dam, bridge, confluence or border ends each stretch) are in `src/dataprep/walloonStretches/recipes.ts`; logic in `src/dataprep/walloonStretches/` is pure and tested on saved OSM extracts in its `fixtures/` folder (make new ones with `scripts/walloon-stretches/save-fixture.mts`).
