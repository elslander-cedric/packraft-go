# packraft-go: project instructions

Route-planning app for packrafting (mixed hike + paddle trips).

## Stack
- Next.js (App Router) + TypeScript, deployed to Vercel Hobby (ADR 0015). Browser-only logic in v1: no API routes, no database (ADR 0011).
- Map: Leaflet with OpenTopoMap tiles. Map components must be client-only (Leaflet needs `window`).
- Routing/snapping/elevation: public BRouter server, hiking profile for hike legs and river profile for paddle legs (ADR 0014). Only route a leg when it changes; store results in the trip.
- UI components: Base UI (`@base-ui/react`), unstyled, via thin wrappers in `src/ui/components/`. Never import Base UI directly in screens. Plain CSS with design tokens as CSS variables (ADR 0020).
- Storage: browser storage + file save/open (ADR 0011).
- Tests: Vitest (unit), Playwright (end-to-end), recorded BRouter responses, never the live server (ADR 0019).
- Free services only (ADR 0012). English UI with strings in one module (ADR 0013).

## Commands
Node 22 (see `.nvmrc`), npm.
- Install: `npm install` (first time also `npx playwright install chromium`)
- Dev server: `npm run dev` (http://localhost:3000)
- Unit tests: `npm test` (Vitest, `src/**/*.test.ts`); watch mode: `npm run test:watch`
- End-to-end tests: `npm run e2e` (Playwright, `e2e/`; builds and starts the app on port 3100, or `E2E_PORT` when set so parallel worktrees don't clash). Use `serveOffline(page)` from `e2e/support/offline.ts` so tiles come from fixtures and no live service is called.
- Lint: `npm run lint`
- Type-check: `npm run typecheck`
- Production build: `npm run build`
- Manual-only scripts (call live services; never in `npm test`, `npm run e2e` or CI). Details in `docs/manual-scripts.md`:
  - `npm run check:brouter` and `npm run check:kiwis`: compare the live BRouter / KiWIS answers with the recorded fixtures (MATCH / DRIFT / MISMATCH; exit 1 = the live app is probably broken). They never write fixtures.
  - `npm run check:kayak` (#218): the same for the SPW's `PKAYAK` map service: the fields of layers 0, 1, 3 and 5, the status codes and the obstacle codes. Never writes fixtures.
  - `npm run check:basemaps`: asks every base map and overlay source for one tile (OK / FAILED; exit 1 = a base map or overlay is probably broken; #179, #180, ADRs 0031, 0032).
  - `npm run data:walloon-stretches` and `npm run review:walloon-stretches`: build and review the Walloon stretch geometry from OSM (#54, ADR 0024), and each record's official stretch against the SPW's lines (#209, ADR 0035).
  - `npm run prepare:spw-data`: prepares the built-in SPW snapshots (official aires, stretches and obstacles) from `PKAYAK` (#206, #214, ADR 0035). Review the diff of `src/access/data/` before committing.

**Layout tests must be font-independent (#70).** The app ships one self-hosted font (Inter, OFL, `public/fonts/`, declared in `globals.css`) so text measures the same on macOS and the Linux CI runner. In layout e2e tests wait for `document.fonts.ready` before measuring, assert the real rule (a figure on one line, Retry fully visible), and never rely on an OS font or a tuned line-count threshold. Don't change the font stack without re-running the layout tests on CI.

CI (`.github/workflows/ci.yml`) runs lint, type-check, unit and e2e tests on every pull request.

## Layout
- `src/app/`: Next.js routes (thin; no domain logic).
- `src/map/`: Leaflet map. `TripMap.tsx` imports Leaflet and must only be loaded through `ClientTripMap.tsx` (no server rendering). `mapConfig.ts` holds the initial view and the base maps (ADR 0031, #179): OpenTopoMap (default), Aerial photos (Belgium) and NGI topo (Belgium), each a stack of tile sources with OpenTopoMap underneath the Belgian ones; `BaseMapTiles.tsx` draws the chosen one and caps the zoom at its max. The choice is `baseMap` in the planner's settings, never in the trip. Overlays (ADR 0032, #180): `overlays` in `mapConfig.ts`, for now only Hiking trails (Waymarked Trails, native tiles to z18), drawn by `OverlayTiles.tsx` in their own pane (`paneZIndex.overlays`) above the base map and below the access layer and the trip; the switched-on ones are `overlays` (a list of `overlayIds`) in the settings. The legs are drawn in their own pane (`paneZIndex.tripLegs`) above the access layer's waters, each on a white casing (`leg-casing`, ADR 0033); their colours and the camp icon are in `tripStyles.ts`. The Map menu (`strings.mapMenuButton`) opens from the layers button (`src/ui/planner/MapMenu.tsx`): the base maps, then the access layer and overlay switches. `serveOffline` serves every base map and overlay source's tiles from the fixture and records each tile's `source` and `baseMap` (null for an overlay); in e2e use the helpers in `e2e/support/mapMenu.ts`.
- `src/core/`: trip planner core (pure TypeScript: trip model, edits, figures, router interface). No React, browser or network imports; a test enforces this. Test fakes live in `src/core/testing/`.
- `src/routing/`: BRouter adapter (implements the core's `Router`). Recorded BRouter responses live in `src/routing/fixtures/` and are shared by unit and e2e tests; `serveOffline(page, { brouter })` replays them.
- `src/persistence/`: browser storage wrapper for autosave of the trip and settings (ADR 0011). Uses the core's versioned save format; never stores undo history. `tripStorage.ts` keeps the trip under `packraft-go.trip`; `settingsStorage.ts` keeps the planner's settings (pace factor, paddling speed, base map, overlays, the side panel's width and whether it is open) under their own key, `packraft-go.settings`, validated by `src/core/settings.ts`. Access points (ADR 0023) are stored separately under `packraft-go.access-points` in their own versioned format, independent of trips.
- `src/dataprep/`: offline data preparation logic (e.g. Walloon stretch geometry from OSM). Pure, used only by scripts in `scripts/` and the offline preparation in `src/access/prepare/`; never imported by app code.
- `src/testing/`: shared test helpers. Test-only; never imported by app code. Includes the offline GPX 1.1 checker (`gpx11.ts`), the hard-coded UI text checker (`hardCodedText.ts`, ADR 0013), and the dependency boundary checker (`dependencyBoundary.ts`, allowlist of runtime dependencies, ADR 0020). To add a runtime dependency, update that allowlist deliberately.
- `src/ui/components/`: thin wrappers around Base UI (ADR 0020): `ConfirmDialog` (Alert Dialog), `ToggleGroup`, `NumberField`, `Menu` (actions, a choice of one among several, and on/off toggles), `TextEntryDialog` (Dialog with one text field), `FormDialog` (Dialog around a small form), `InfoDialog` (Dialog that only shows information, with Close), `SidePanel` (the sheet's sideways counterpart; its left edge is a splitter that resizes it by drag or arrow keys, within the limits in `sidePanelWidth.ts`, ADR 0034, #188), `SearchBox` (Autocomplete with its own filtering off: a search field whose dropdown shows the answer to a submitted search, never suggestions as you type; #173; `inline` puts the answer under the field instead of a popup, #174) and `Button`, each with its own stylesheet. The four dialogs share `Dialog.css` (flat panel with the sheet's corners, a divider under the title, 44 px buttons and fields; the main action is `button-primary`). Every dialog sits in the visible area above an on-screen keyboard (`useVisibleArea` in `visibleArea.ts` follows `window.visualViewport`; #163); `TextEntryDialog` opens with its field focused, `FormDialog` opens without the keyboard on a touch screen. Screens import these, never `@base-ui/react`; `boundary.test.ts` enforces this. Wrappers take their text as props from the screens. Design tokens (colours, spacing) are CSS variables at the top of `src/app/globals.css`. In e2e tests, answer confirmations with `e2e/support/confirmDialog.ts`.
- `src/ui/icons/` (ADR 0028, #143): the UI icons, Font Awesome Free Solid, the only place that imports `@fortawesome/free-solid-svg-icons` (`boundary.test.ts` enforces this). `icons.ts` names each icon by its use, `Icon` draws one in a screen and `iconSvg()` as a string for Leaflet markers; both use `currentColor`. Icon-only buttons keep their accessible names in `strings.ts`.
- `src/access/` (+ `src/core/access.ts`): the access layer (ADRs 0022, 0024). Built-in rule data with a source and research date per record, prepared offline with `npm run prepare:access-data` (never queried at runtime), and the pure access-status evaluation in the core (Walloon AGW rules in `src/core/agw.ts`; `src/access/walloon.ts` adapts `src/data/walloon-stretches.json` at load time). See `src/access/README.md`.
- Official aires (ADR 0035, #206): `OfficialAire` and `OfficialStretch` in `src/core/officialAire.ts`, a read-only type of their own, not an `AccessPoint`, never written to access point storage, trips or settings. Built-in snapshots `src/access/data/official-aires.json` and `official-stretches.json` (ids and names only; no lines shipped), prepared offline by `scripts/prepare-spw-data.mts` with the pure, tested logic in `src/access/prepare/spw.ts`; never queried at runtime. `builtInOfficialAires` (`src/access/builtInOfficialAires.ts`, apart from the rules so the planner can load them from a trip's first point) adds each aire's id and the snapshot's source and date on load. The aire warning and snap offers (`aireWarnings`, `snapCandidate`; #207) take them beside your access points: a built-in aire must fit the put-in or take-out, your official-aire marks count whatever their use, and a `SnapOffer`'s target is either kind. Accepting one moves the trip point only. `src/map/OfficialAireLayer.tsx` draws them with the access layer in the locks' pane: every aire at any zoom, small and not tappable below `aireFullMarkersMinZoom`, a 44 px target from it. A tap opens `OfficialAireDetail` in `AccessDetailsDialog`, which shows the access status of the aire's stretch on the access layer's date (`officialStretchAccess` in the core, #213: every record on the stretch, the most restrictive wins), worded by `statusReasonTexts` in `src/ui/reasonText.ts`. `useAccessLayer` loads the rules, flows and official status while an aire is open, also with the layer off.
- Obstacles (ADR 0035, #214): `Obstacle` and `obstacleKinds` in `src/core/obstacle.ts`. Built-in snapshot `src/access/data/obstacles.json`, prepared by the same script from layer 1: the kind comes from `codico` alone (the script fails on any other code), and the name and meaning are the app's own in `strings.obstacles`, as the SPW publishes only a position. `builtInObstacles` adds each one's id and the snapshot's source and date on load. `src/map/ObstacleLayer.tsx` draws them with the access layer in the locks' pane from `lockMarkersMinZoom`, small and not tappable below `obstacleFullMarkersMinZoom`, a 44 px target from it, each kind with its icon from `obstacleIcons`. A tap opens `ObstacleDetail` in `AccessDetailsDialog`. Warnings (#215): `tripAccess` gives a paddle leg an `obstacleWarnings` entry per obstacle within `LOCK_TOLERANCE_M` of its line, in the order it meets them (`obstaclesOnLine`), beside `lockWarnings` on legs, days and sections; never by date or flow, and never blocking. `dayWarnings` counts them as the `obstacle` kind. A leg's details show one line per kind (`obstacleGroups`), so a long stretch stays readable.
- `src/hydrometry/` (ADR 0024, #61): the KiWIS client, the only module that talks to the SPW hydrometry service. `kiwis.ts` implements the core's `FlowSource` (two batched requests per refresh, each with a 15-second timeout; answers and failures cached for 15 minutes); `liveCheck.ts` is the manual contract check (#64). Recorded KiWIS answers live in `src/hydrometry/fixtures/` (see its README) and are shared by unit and e2e tests (`kiwisFixtures(...)` in `e2e/support/offline.ts`). The pure flow rules are in `src/core/flow.ts`.
- `src/kayak/` (ADR 0035, #210): the `PKAYAK` client, the only module of the app that talks to the SPW's kayak map service (the manual `scripts/prepare-spw-data.mts` calls it too, offline from the app). `pkayak.ts` implements the core's `OfficialStatusSource`: a refresh is at most two requests, layer 5 (no geometry, four fields) and layer 0 (incidents, #216), each made only when asked for, which fail apart, each with a 15-second timeout; answers and failures are cached for 15 minutes; the REST API at `kayak.spw.wallonie.be` isn't used. The page shares one source through `src/ui/useOfficialStatus.ts`: the status is asked for only while something is shown for today or later, incidents also for a paddle leg on any date or none. Live answers (official status, incidents, KiWIS flows) go through `createLiveFeed` in `src/ui/liveFeed.ts`: one answer per page for the map and the trip, asked again 15 minutes after each answer while wanted and never while nothing wants it, so a failure heals; the adapters' caches keep the cap. The built-in chunks in `useAccessRules.ts` use it too, retrying a failed load every minute (`keepOnSuccess` never keeps a failed import), and with no rules a status reads unknown, not checking. `liveCheck.ts` is the manual contract check (#218). Recorded answers live in `src/kayak/fixtures/` (see its README) and are shared by unit and e2e tests (`serveOffline(page, { kayak: kayakFixture(...), incidents: kayakFixture(...) })`; without `kayak` it answers 503, so today's computed status stands; without `incidents` there are none). The code mapping is in `src/core/officialStatus.ts`; `evaluateAgw` in `src/core/access.ts` lets a reading replace the flow check on today's date, and a calendar closure still applies. The reason carries the verdict as `official`, and `reasonText` in `src/ui/reasonText.ts` words it with `strings.official`. Incidents are in `src/core/incident.ts` and never reach `accessAt`, so they can't change an access state; `src/map/IncidentLayer.tsx` draws them at any zoom, and `officialNotChecked(status, incidents)` adds them to the note when they fail. While the access layer is on, `MapNotCheckedNote` (`checksFailed` in the core) says so without a tap, under the access chip, and only its link takes taps.
- `src/geocoding/` (ADRs 0027, 0030; #136, #172): the Nominatim client, the only module that talks to Nominatim and the only one that sends access point positions anywhere. `createNominatim()` in `nominatim.ts` is one client with one line (requests at least a second apart; a waiting search goes before waiting default names) serving both the core's `DefaultNameSource` (reverse geocoding to "road, place" in local names) and its `PlaceSearchSource` (`src/core/placeSearch.ts`: place search sends only the text and the visible area, answers kept in memory for the session, failures not). The page shares one lazily imported client through `src/ui/sharedNominatim.ts`. `src/ui/defaultNames.ts` works through the points waiting for a default name whenever the app is online. Recorded answers live in `src/geocoding/fixtures/` (see its README); e2e tests replay them with `nominatimFixture(...)` or `nominatimFixtures({ reverse, search })` in `e2e/support/offline.ts`.
- Place search (#173, #174, ADR 0030): `parseCoordinates` and the search reducer in `src/core/placeSearch.ts` (not part of the planner session), `usePlaceSearch` in `src/ui/` (shared Nominatim client), the field and its results in `src/ui/PlaceSearchBar.tsx` and the result's pin in `src/map/SearchResultLayer.tsx`. `src/ui/planner/PlaceSearch.tsx` is a pill on the top row between the menu and the right-hand buttons that opens into the inline field, above the keyboard (`useVisibleArea`); the access chip sits on a second row under it, right-aligned beside the layers button. A result is fitted into the part of the map the pill, sheet or side panel leave free (`searchCover` in `Planner`).
- `src/pwa/` and `public/sw.js`: PWA registration and a hand-written service worker (ADR 0023). It caches the same-origin app shell only, never map tiles, BRouter, KiWIS, PKAYAK or Nominatim.
- `src/ui/planner/` (+ `src/map/TripMap.tsx`): the one planner (ADRs 0026, 0034), on every screen (`ClientTripPlanner` loads `Planner`): a full-screen map with floating buttons and, in portrait at width ≤ 640 px, a bottom sheet, everywhere else the resizable side panel on the right (`SHEET_QUERY` in `usePlannerLayout.ts`), with the Sections and Days tabs (the Access points tab in access point editing), and a layers button that opens the Map menu (base maps, access layer and overlay switches; #179, #180); the trip's name and start date (Edit trip, #154) and the settings (#151) are dialogs from its menu (New trip, Edit trip, Save trip, Open trip | Export GPX | Settings, with icons). It runs `usePlanner` and adds no planning rules. Its text is in `strings.planner`, its styles in `planner.css` (classes `planner-*`). Leg and section rows are one `TripRow`; `SectionsList` and `SectionDetailsDialog` show a section's totals (`TripSummary.sections`) and its legs' warnings (`legsAccess`, ADR 0029); a tap on the selected section of several legs opens it to show its legs (#200), and `Planner` keeps which are open by first leg; its legs sit in line with it on a grey band. A section or leg with details has an Access details button on its row, at the right of the last line, or under the routing state while there is one; it only opens the dialog. `DaysPanel`, `SnapOffers`, `TripAccessView` and `AccessPanel` (the access legend, date and details) stay in `src/ui/`. In e2e on a desktop-sized window use the helpers in `e2e/support/planner.ts` (the trip panel, its tabs, the menu, Open/Save trip, clicks on the free part of the map); `showAllLegs(page)` opens every section as it appears, for specs about legs. Specs that use access points enter access point editing first with `enterAccessPointEditing(page)` from `e2e/support/accessPointEditing.ts` (`markAccessPointAt` does it for you).
- `src/ui/planner/AccessPoints.tsx` + `AccessPointDialog.tsx` (#63, ADR 0023): your access points, changed only in *access point editing* (ADR 0036, #225), the planner's second mode: `mode` in the planner session (`{ kind: "normal" }` or `{ kind: "accessPointEditing", returnTo }`, set by the `enterAccessPointEditing` and `leaveAccessPointEditing` actions), never in settings, so the planner always opens in normal mode. A floating button bottom left enters it; a banner ("Editing access points") has Done to leave. Normal mode shows only the Sections and Days tabs and no mark button; access point editing only the Access points tab and the mark button. Entering opens the panel or sheet on that tab, also from closed; Done restores the tab, the sheet's stop and whether the panel was open (`returnTo`). Both clear the selection. In normal mode your access point markers are inert (#226: `editable` on `AccessPointLayer`, not interactive, not focusable): a press passes through to the route point, leg or map under it, while snap offers still move trip points onto them and official aires stay tappable. While editing the trip is frozen (#227): the planner session ignores the actions that change its points or leg modes, select a point or answer a snap offer (`frozenWhileEditing`); `TripMap` gets `frozen`, so route points and legs have no hit areas and a press reaches your access points; back to start, delete, camp, undo and their keys are off, the snap offers wait for Done, and a map tap only places an access point in place mode. There is no action that makes the selected route point an access point. In access point editing, mark one with the floating button at your GPS position (or by tapping the map when there is no fix), which opens its details dialog. While the trip has a route the tab lists the points on the route first in route order, then the rest nearest to you (#156; the split is `accessPointsByRoute` in `src/core/onRoute.ts`); each row has edit and delete buttons, and the marker drags to correct it. Official aires on the route (`officialAiresOnRoute`, #208) are merged into the route-ordered part as read-only rows that open `AccessDetailsDialog`, with the access layer on or off; off-route ones aren't listed. The dialog keeps a draft; Save stores it on the device at once by `useAccessPoints`, with or without signal.
- `src/ui/strings.ts`: all user-facing text (ADR 0013).

## Agent lessons
Project-specific rules for agents working in this repo (learned in past PRs).
- **Ports:** each agent gets its own port. Set `E2E_PORT` for `npm run e2e` (e.g. 3101, 3102, …) and pass `-- --port <n>` to `npm run dev`, so parallel worktrees don't test each other's builds.
- **Dates:** no time-zone drift: a date picked in Europe/Brussels must not move a day.
- **No live services in tests (ADR 0019):** use `serveOffline(page)` and recorded fixtures, and prove it, e.g. by blocking `fetch` or the network and re-running.
- **New runtime dependency:** update the allowlist in `src/testing/dependencyBoundary.ts` deliberately.
- **Edge cases that bit us:** trip names with `/ : & <` or control characters (GPX/XML must stay well-formed, inner names must match file names; #24, #45); longitudes rounding to 180 (GPX needs < 180; #24); unlisted Walloon water must read "not allowed", not "unknown" (#75).
